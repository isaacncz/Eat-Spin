# Destination search (#122)

The Spin screen can search around an area, landmark, or address without GPS permission. Selecting a provider-confirmed shopping mall defaults to **Inside this mall**; **Around this mall** explicitly enables radius search. Current-location and around-destination searches share 1, 3, 5 and 10 km radius presets. A new user defaults to 5 km; saved selections are retained and legacy walk/drive preferences migrate to 1/5/10 km. Choosing a destination retains the current radius preference, hidden during inside-only searches. Travel hints are approximate rather than routed travel times. “Open now only” defaults on, can be disabled for planning, and does not predict arrival-time availability.

Device GPS remains separate for location-based favourites and Discover. Destination changes reset the round/result and cancel obsolete requests. Nearby cache selection retains center, radius, cuisine, and availability dimensions. Text Search uses the circle's bounding rectangle where possible, then an exact distance filter; polar/date-line circles fall back to circular bias and the same exact filter.

## Persistence

`eatspin:search-destination:v1` stores place ID, coordinates, original fetch time, radius, and (for mall selections) the mall place ID and user's scope preference. It excludes Google-derived names/addresses/types, typed queries, session tokens, and GPS coordinates. Names and addresses stay in memory. After reload, the center is labelled “Saved destination”; selecting a place again restores its live label. No Details lookup is made solely for reload. Invalid records and coordinates aged 30 days are discarded; their age is never extended by reload. An expired inside-only selection retains only its mall ID as a pending selection and requires reselecting a destination or explicitly choosing current location; it never silently falls back to GPS. Selecting current location clears the saved destination while retaining the radius preference. Storage failure leaves in-memory selection usable.

## Mall membership (#131)

Destination Details includes `types` to detect `shopping_mall`, retaining the Essentials field tier. The selected mall defaults to inside-only. Nearby and Text Search request `places.containingPlaces`; only an exact containing place ID match admits a restaurant. An absent relationship is unknown and excluded. Neither a mall-like name, an address mentioning the mall, nor coordinates establish membership. Existing selections saved before mall detection need reselecting to identify them as malls.

Inside-only searches discover candidates within a fixed 2 km area. This is a discovery bound, not a mall boundary: membership is checked before ranking/limiting, and the saved user radius is not an eligibility filter. The provider returns a limited candidate set (Nearby: up to 20); missing relationships and candidate limits can omit real tenants. This is not a complete mall directory. Sunway Pyramid coverage has not been validated against live tenant data. Official-directory augmentation is deferred until there is a verified source and correct branch mapping.

The scope and active mall ID participate in request identities, cancellation and wheel resets. Inside snapshots and their underlying place records have separate keys from around searches and from other malls. Cached tenants are rechecked for the selected mall before use. Legacy unrestricted snapshots cannot satisfy inside-only lookups. API failures may use an eligible scoped snapshot, but never bundled fallback restaurants or unrestricted caches. Empty/error states preserve scope and offer explicit nearby search or another destination. Resetting ordinary filters does not widen scope. Text search, round review and result labels share the same inside-only intent.

This is a deliberate adjustment to the initial issue persistence sketch after the policy check: the generic Places storage exception covers place IDs and temporary coordinates, not cached names/addresses.

## Google documentation verified 2026-10-23

- [Autocomplete session pricing](https://developers.google.com/maps/documentation/places/web-service/session-pricing): for sessions ending in Details Essentials, the first 12 autocomplete requests are charged individually, subsequent requests in that completed session have no charge, and the terminating Details request is billed separately. Abandoned sessions charge every autocomplete request.
- [Session tokens](https://developers.google.com/maps/documentation/places/web-service/place-session-tokens): generate a UUID per session, reuse it across suggestions and the single terminating Details call, then discard it. All calls use the same project's key. Closing the picker abandons its session; failed/interrupted selection never reuses the token.
- [Details field mask](https://developers.google.com/maps/documentation/places/web-service/place-details): `location,formattedAddress,types` uses Essentials. The display label comes from autocomplete; `displayName` is not requested. The `types` tier was rechecked against the [field table](https://developers.google.com/maps/documentation/places/web-service/data-fields) on 2026-11-06.
- [ContainingPlace](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places#ContainingPlace) provides the containing place's ID. `containingPlaces` is available in Nearby/Text Search at the Pro tier; the app's existing richer restaurant masks already request higher-tier fields. No additional per-restaurant Details fan-out is added for membership.
- [Text Search](https://developers.google.com/maps/documentation/places/web-service/text-search): rectangular `locationRestriction` and `locationBias` are mutually exclusive. Rectangle restriction is a pre-filter, not an exact circular boundary.
- [Places policies](https://developers.google.com/maps/documentation/places/web-service/policies) and [service terms §14.3](https://cloud.google.com/maps-platform/terms/maps-service-terms): place IDs may be stored; coordinates may be temporarily cached for up to 30 days. Do not persist destination names or formatted addresses. The compact picker attributes its Google-sourced content with “Google Maps” text.

## Operator setup

Use the existing `VITE_GOOGLE_MAPS_API_KEY`, `VITE_GOOGLE_PLACES_REGION` (default MY), and language (default en). Region is formatting/ranking context, not a country restriction on suggestions. Enable Places API (New) and check the key's allowed applications/APIs for Autocomplete, Details, Nearby, and Text Search.

Publish the updated `docs/firebase-rtdb-rules.json` usage rule before releasing this client to a Firebase-configured environment: it adds `autocomplete` and `details` counter kinds. Without those writes, lookup reports the permission failure and does not silently bypass shared budgeting. The existing local-storage fallback remains available when Firebase is unconfigured.

Each new kind uses the existing configured monthly cap/threshold as a conservative request guard, not a dollar estimator or promise of free usage. Every autocomplete request reserves a slot even if a completed session may later receive discounted billing. Failed/aborted requests may consume reservations. Keep Google Cloud quotas as the hard backstop. Existing restaurant caching policy is outside this feature's scope.
