# Destination search (#122)

The Spin screen can search around an area, landmark, or address without GPS permission. Selecting a provider-confirmed shopping mall defaults to **Inside this mall**; **Around this mall** explicitly enables radius search. Current-location and around-destination searches share 1, 3, 5 and 10 km radius presets. A new user defaults to 5 km; saved selections are retained and legacy walk/drive preferences migrate to 1/5/10 km. Choosing a destination retains the current radius preference, hidden during inside-only searches. Travel hints are approximate rather than routed travel times. “Open now only” defaults on, can be disabled for planning, and does not predict arrival-time availability.

Device GPS remains separate for location-based favourites and Discover. It is a fixed anchor: `useLocation` takes one fix per request (`getCurrentPosition`) and never follows the device, so driving does not rebuild the wheel or repeat Places searches. "Use my current location" (and Group "Find places" around the host) takes a new fix; while it is pending the previous fix is not used for a search, and a fix within 100 m of the current anchor keeps it. If a refresh fails or never answers (it gives up after 15 s), the last anchor stays and the error is shown. Destination changes reset the round/result and cancel obsolete requests. Nearby cache selection retains center, radius, cuisine, and availability dimensions. Text Search uses the circle's bounding rectangle where possible, then an exact distance filter; polar/date-line circles fall back to circular bias and the same exact filter.

## Persistence

`eatspin:search-destination:v1` stores place ID, coordinates, original fetch time, radius, and (for mall selections) the mall place ID and user's scope preference. It excludes Google-derived names/addresses/types, typed queries, session tokens, and GPS coordinates. Names and addresses stay in memory. Non-mall destinations retain the “Saved destination” label on reload. Saved malls make one guarded, non-session Details lookup for `displayName,formattedAddress,types` to restore their runtime address identity; this uses the Pro field tier and does not extend the original coordinate age. Discovery waits for that lookup. If it fails, exact provider relationships remain usable, with no address fallback. Names and addresses are not added to saved destination storage. Invalid records and coordinates aged 30 days are discarded; their age is never extended by reload. An expired inside-only selection retains only its mall ID as a pending selection and requires reselecting a destination or explicitly choosing current location; it never silently falls back to GPS. Selecting current location clears the saved destination while retaining the radius preference. Storage failure leaves in-memory selection usable.

## Mall membership (#131)

Destination Details includes `types` to detect `shopping_mall`, retaining the Essentials field tier for picker selections. The selected mall defaults to inside-only. Before membership or cuisine matching, Google places must have a positive food-service classification from `primaryType`, or from specific `types` when the primary type is missing. An explicit non-food primary identity overrides incidental food tags. Restaurant/cuisine subtypes, cafés, bakeries, dessert places, food courts, takeaway and drink venues remain supported. Retail, services and generic `food`/`point_of_interest` records are excluded; food-like names, summaries and mall addresses cannot qualify them. The derived `venueKind` stays separate from cuisine categories and is rechecked for mall cache reads. Legacy mall snapshots without this classification are invalidated. No new API fields or classification requests are added. The [Google place-type taxonomy](https://developers.google.com/maps/documentation/places/web-service/place-types) was checked on 2026-11-07.

Both discovery and food search use the same membership resolver:

- An exact `containingPlaces` ID match admits a restaurant.
- If there are no containing-place IDs, the formatted address must identify the selected mall building and include a tenant unit/floor or the mall's road and postcode. Matching normalizes case, punctuation, and common road abbreviations. Mall-name mentions alone, shared roads/postcodes and coordinates are insufficient.
- Conflicting containing-place IDs, vicinity phrases, hotel/resort/annex/tower addresses, extended building names and conflicting postcodes do not qualify through the address path. Ambiguous records remain excluded. Exact provider membership takes priority.

With runtime mall identity available, discovery uses a mall-name/address-qualified Text Search (`restaurants in <mall>, <base address>`), rather than filtering one area's popular Nearby results. Food queries use the same qualification. A fixed 2 km rectangle limits discovery, not membership. Text Search follows up to three pages of 20 candidates with an unchanged query and deduplicates place IDs. Every page reserves the existing `text` budget before fetching, respects cancellation and checks repeated tokens. Errors or budget exhaustion fail the operation; they never substitute unrestricted candidates. Without runtime identity, the strict relationship-only Nearby/Text path remains available.

The existing wheel pool still ranks/limits results (20 by default), and availability, review quality, cuisine, price and avoided-place filters can reduce the visible count. The count is eligible picks, not the mall's total restaurant count. No complete tenant-directory coverage is promised. Real Google Places responses for Sunway Pyramid have not been validated.

Official Sunway Pyramid directory pages checked on 2026-11-07 confirm example lot/floor formats: [Dookki, LG1.110](https://www.sunwaypyramid.com/directory/dookki), [Oga Tea & Dining, LG1.122C](https://www.sunwaypyramid.com/directory/oga-tea-and-dining), and [Longjing, LG1.107&108](https://www.sunwaypyramid.com/directory/longjing). Tests model these address patterns; they do not claim to be captured live Google responses. Official-directory ingestion and verified provider branch mapping remain follow-up work in #135.

The scope and active mall ID participate in request identities, cancellation and wheel resets. Inside snapshots and their underlying place records have separate keys from around searches and from other malls. Cached tenants are rechecked for the selected mall before use. Legacy unrestricted snapshots cannot satisfy inside-only lookups. Mall snapshots carry a membership version; snapshots from the old discovery strategy are invalidated. Runtime mall identity is passed to cache filtering but is never stored in snapshot metadata. API failures may use an eligible scoped snapshot, but never bundled fallback restaurants or unrestricted caches. Empty/error states preserve scope and offer explicit nearby search or another destination. Resetting ordinary filters does not widen scope. Text search, round review and result labels share the same inside-only intent.

This is a deliberate adjustment to the initial issue persistence sketch after the policy check: the generic Places storage exception covers place IDs and temporary coordinates, not cached names/addresses.

## Google documentation verified 2026-10-23

- [Autocomplete session pricing](https://developers.google.com/maps/documentation/places/web-service/session-pricing): for sessions ending in Details Essentials, the first 12 autocomplete requests are charged individually, subsequent requests in that completed session have no charge, and the terminating Details request is billed separately. Abandoned sessions charge every autocomplete request.
- [Session tokens](https://developers.google.com/maps/documentation/places/web-service/place-session-tokens): generate a UUID per session, reuse it across suggestions and the single terminating Details call, then discard it. All calls use the same project's key. Closing the picker abandons its session; failed/interrupted selection never reuses the token.
- [Details field mask](https://developers.google.com/maps/documentation/places/web-service/place-details): `location,formattedAddress,types` uses Essentials. The picker display label comes from autocomplete; picker selections do not request `displayName`. Saved-mall rehydration separately requests `displayName` at Pro tier. The `types` tier was rechecked against the [field table](https://developers.google.com/maps/documentation/places/web-service/data-fields) on 2026-11-06.
- [ContainingPlace](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places#ContainingPlace) provides the containing place's ID. `containingPlaces` is available in Nearby/Text Search at the Pro tier; the app's existing richer restaurant masks already request higher-tier fields. No additional per-restaurant Details fan-out is added for membership.
- [Text Search](https://developers.google.com/maps/documentation/places/web-service/text-search), rechecked 2026-11-07: `pageSize`, `nextPageToken` and `pageToken` support up to 60 results across pages; all parameters other than page token/size must remain unchanged. Each page is a separate guarded request, using the existing rich restaurant field mask; the guard is not a dollar estimator. Rectangular `locationRestriction` and `locationBias` are mutually exclusive. Rectangle restriction is a pre-filter, not an exact circular boundary.
- [Places policies](https://developers.google.com/maps/documentation/places/web-service/policies) and [service terms §14.3](https://cloud.google.com/maps-platform/terms/maps-service-terms): place IDs may be stored; coordinates may be temporarily cached for up to 30 days. Do not persist destination names or formatted addresses. The compact picker attributes its Google-sourced content with “Google Maps” text.

## Operator setup

Use the existing `VITE_GOOGLE_MAPS_API_KEY`, `VITE_GOOGLE_PLACES_REGION` (default MY), and language (default en). Region is formatting/ranking context, not a country restriction on suggestions. Enable Places API (New) and check the key's allowed applications/APIs for Autocomplete, Details, Nearby, and Text Search.

Publish the updated `docs/firebase-rtdb-rules.json` usage rule before releasing this client to a Firebase-configured environment: it adds `autocomplete` and `details` counter kinds. Without those writes, lookup reports the permission failure and does not silently bypass shared budgeting. The existing local-storage fallback remains available when Firebase is unconfigured.

Each new kind uses the existing configured monthly cap/threshold as a conservative request guard, not a dollar estimator or promise of free usage. Every autocomplete request reserves a slot even if a completed session may later receive discounted billing. Failed/aborted requests may consume reservations. Keep Google Cloud quotas as the hard backstop. Existing restaurant caching policy is outside this feature's scope.

## Group nearby fill

Hosts and co-hosts can fill a Group room from a Google Maps nearby search ("Find places nearby" in the room editor). The center is the host's device location or a searched area; members never call Google and read the shared room list. One Nearby Search runs on the host's device and counts against the shared `nearby` budget; the panel is disabled while that budget is blocked.

Ticked places are written through the normal room-list transaction. Names are shortened to the 24-character room limit with an ellipsis, and each item also stores its Google `placeId` (rules allow `^[A-Za-z0-9_-]{1,256}$`). Members' result links use `query_place_id` so a shortened name still opens the right place.

Policy note: room items are Google-derived names stored in Firebase for the room's lifetime (2 hours); expired rooms are removed when next opened. This is a product decision accepted with known policy risk, not a confirmed exception to the Places caching terms above. "Save a personal copy" keeps the shortened names locally, as it does for other room lists.

Publish the updated `docs/firebase-rtdb-rules.json` (room-list `placeId` validation) with the client. Older clients ignore `placeId`.
